# ADR-001: Adopción de Kong como API Gateway

- **Estado:** Aceptado
- **Fecha:** AAAA-MM-DD
- **Responsables:** Equipo de Arquitectura / Plataforma
- **Decisión:** Utilizar Kong API Gateway
- **Ámbito:** Enrutamiento, seguridad, gestión de tráfico y observabilidad
- **Relacionado con:** [SDLC and Tools](../sdlc-and-tools.md)

## 1. Contexto

La plataforma se encuentra en un proceso de modernización basado en el
patrón arquitectónico **Strangler Fig**. Este patrón permite reemplazar
gradualmente funcionalidades del sistema monolítico por nuevos
microservicios, sin realizar una migración completa en un único cambio.

Durante esta transición coexistirán:

- El sistema monolítico.
- Los nuevos microservicios.
- Diferentes versiones de las API.
- Aplicaciones web y móviles.
- Consumidores internos y externos.
- Servicios compartidos de autenticación y observabilidad.

Esta convivencia requiere un punto de entrada centralizado que permita
determinar dinámicamente si una solicitud debe ser dirigida al monolito
o a un microservicio.

Además del enrutamiento, la plataforma necesita aplicar de manera
consistente políticas transversales de:

- Autenticación.
- Autorización.
- Balanceo de carga.
- Rate Limiting.
- Throttling.
- CORS.
- Auditoría.
- Registro de solicitudes.
- Métricas y observabilidad.

Implementar estas capacidades individualmente en cada servicio produciría
duplicación de código, configuraciones inconsistentes y un mayor costo
de operación y mantenimiento.

## 2. Problema

Se necesita seleccionar un API Gateway que funcione como punto de entrada
estándar para las API y que permita:

1. Enrutar solicitudes entre el monolito y los microservicios.
2. Cambiar gradualmente el destino del tráfico durante la migración.
3. Balancear solicitudes entre varias instancias de un servicio.
4. Centralizar la autenticación y la autorización.
5. Aplicar políticas de protección y control de tráfico.
6. Proporcionar registros, métricas y datos de auditoría.
7. Administrar la configuración como código.
8. Integrarse con el pipeline de CI/CD.
9. Evitar cambios en los consumidores durante la migración.
10. Reducir la implementación de lógica transversal dentro de los servicios.

## 3. Fuerzas de decisión

La solución seleccionada debe cumplir, como mínimo, con los siguientes
criterios:

| Criterio | Descripción |
|----------|-------------|
| Enrutamiento dinámico | Enviar solicitudes al monolito o a los microservicios según rutas y reglas |
| Balanceo de carga | Distribuir tráfico entre múltiples instancias |
| Seguridad | Integrarse con OAuth 2.0, OpenID Connect y JWT |
| Gestión de tráfico | Aplicar Rate Limiting, CORS, restricciones y otras políticas |
| Observabilidad | Proporcionar logs, métricas y correlación de solicitudes |
| Automatización | Permitir configuración declarativa e integración con CI/CD |
| Extensibilidad | Incorporar nuevas capacidades mediante plugins |
| Escalabilidad | Atender el crecimiento de solicitudes y servicios |
| Portabilidad | Ejecutarse en distintos ambientes e infraestructuras |
| Operabilidad | Facilitar administración, monitoreo y diagnóstico |
| Compatibilidad | Integrarse con el monolito y los nuevos microservicios |
| Adopción gradual | Permitir migrar servicios sin cambiar las URL públicas |

## 4. Opciones consideradas

### 4.1 Kong API Gateway

Plataforma de gestión de API basada en un modelo de servicios, rutas,
upstreams, targets, consumidores y plugins.

Ofrece capacidades de:

- Enrutamiento basado en rutas, hosts, métodos y encabezados.
- Balanceo de carga y verificaciones de salud.
- Aplicación de políticas mediante plugins.
- Validación de JWT y otros mecanismos de autenticación.
- Rate Limiting y control de tráfico.
- Administración declarativa y automatización.
- Integración con herramientas de observabilidad.
- Ejecución en contenedores y Kubernetes.
- Operación en diferentes modalidades de despliegue.

### 4.2 Enrutamiento personalizado en el monolito

Consiste en implementar dentro del monolito la lógica necesaria para
redirigir solicitudes hacia los nuevos microservicios.

Esta opción fue descartada porque:

- Aumenta el acoplamiento con el sistema que se desea retirar.
- Incorpora nuevas responsabilidades en el monolito.
- Dificulta la evolución independiente de la plataforma.
- Requiere desarrollar capacidades ya disponibles en un API Gateway.
- Complica la aplicación uniforme de políticas de seguridad.
- Convierte el monolito en un posible cuello de botella.

### 4.3 Enrutador o proxy inverso básico

Consiste en utilizar únicamente un proxy inverso para dirigir las
solicitudes según la URL.

Esta opción puede resolver el enrutamiento básico, pero requeriría
componentes o implementaciones adicionales para:

- Gestión de consumidores.
- Autenticación y autorización.
- Rate Limiting avanzado.
- Administración de políticas por servicio o ruta.
- Auditoría.
- Configuración orientada al ciclo de vida de las API.

Se descartó como solución principal porque no cubre de forma integrada
todos los requisitos del caso práctico.

### 4.4 Implementar las políticas en cada microservicio

Consiste en hacer que cada servicio implemente individualmente
autenticación, CORS, límites de tráfico, auditoría y otras políticas.

Esta opción fue descartada porque:

- Duplica lógica transversal.
- Puede producir comportamientos inconsistentes.
- Aumenta el esfuerzo de desarrollo y pruebas.
- Dificulta aplicar cambios globales.
- Incrementa el riesgo de errores de configuración.
- Obliga a mantener las mismas capacidades en diferentes tecnologías.

Los microservicios continuarán aplicando controles de seguridad propios,
pero las políticas comunes de borde se centralizarán en el gateway.

### 4.5 Otras plataformas de API Gateway

También pueden existir otras soluciones comerciales, de nube o de código
abierto capaces de cubrir parte o la totalidad de los requisitos.

Sin embargo, para este caso se selecciona Kong por:

- Su modelo de configuración orientado a API.
- Su arquitectura extensible mediante plugins.
- Su compatibilidad con despliegues modernos.
- Su capacidad para ejecutarse en infraestructura administrada por la
  organización.
- La posibilidad de administrar rutas y políticas como código.
- Su adecuación al patrón Strangler Fig.
- Su soporte para balanceo, seguridad, control de tráfico y observabilidad.

La comparación definitiva de costos, soporte y características debe
realizarse de acuerdo con la edición y modalidad de Kong seleccionadas.

## 5. Decisión

Se utilizará **Kong API Gateway** como punto de entrada estándar para las
API de la plataforma.

Kong se ubicará entre los consumidores y los servicios internos:
